Data Science with Kixi.stats, part 2

After some exploration and analysis of the data it’s time to create a predictive model. In this episode you’ll discover several new chart types, learn how to evaluate the correlation between variables, how to create a simple linear model, and how to evaluate the fitness of the model.

Transcript

In part one of this series you got set up with Kixi.stats and thi.ng/geom, and had an initial critical look at the data, in particular at the abalone ring count, since this is the value to predict based on other variables.

It turned out the ring count’s distribution approximates a Log-Normal distribution, which is an important bit of information.

That was all just warm up, now it’s time to look at the other variables, see how they correlate with the value you’re trying to predict, use them to create a predictive model, and see how well the model actually is at predicting.

Like last time everything you need is in the associated Github repo, just open the core namespace, connect a REPL and you’re good to go.

Last episode I jumped straight into drawing scatterplots, but the graphical equivalent of the five-number summary is the so-called box plot or box-and-whiskers-plot.

They’re not quite as intuitive as say a simple bar chart, but once you know how to read them they should be clear as day.

Box plots represent distributions, so to get a feel of what a “normal” box plot looks like I’ll create a box plot for a “standard normal distribution”, meaning a Normal Distribution with a mean of 0, and a standard deviation of 1.

kixi.stats has all kinds of distributions built-in, which is great for exploring statistical properties. I’ll create a normal distribution and then sample 10000 numbers from it, so I have a normally distributed data set to play with.

(def standard-normal (kixi.dist/normal {:mu 0 :sd 1}))
(def standard-normal-sample (kixi.dist/sample 10000 standard-normal))

(transduce identity kixi/summary standard-normal-sample)
;; => {:min -3.8519271282006016,
;;     :q1 -0.6659900852641175,
;;     :median -0.01714498352689695,
;;     :q3 0.6686650777464612,
;;     :max 3.5555441959666005,
;;     :iqr 1.3346551630105787}

You already know the histogram, which shows that characteristic bell curve associated with the Normal Distribution. The box plot is a different way of summarizing this distribution. It’s a bit easier to explain if I draw these on top of each other, making sure the x-axes lines up.

That thick line in the middle of the box is the median, and the left and right edges of the box are the first and third quartile. So half of all data falls within that range covered by the box.

(g/open (g/histogram {:data standard-normal-sample}))
(g/open (g/box-plot {:data standard-normal-sample}))

(g/open (g/vbox (g/histogram {:data standard-normal-sample
                              :bin-count 50
                              :left-margin 70
                              :x-domain [-5 5]})
                (g/box-plot {:data standard-normal-sample
                             :left-margin 70
                             :x-domain [-5 5]})))

The “whiskers” sticking out left and right of the box extend 1.5 times the interquartile range from the first and third quartile. You can calculate that yourself using the five number summary. So the left whisker shows the smallest value in the data set that is bigger than -2.73, and the right whisker shows the biggest value smaller than 2.77.

(let [{:keys [q1 iqr q3]}
      (transduce identity kixi/summary standard-normal-sample)]
  [(- q1 (* 1.5 iqr)) (+ q3 (* 1.5 iqr))])
;; => [-2.7308179100554195 2.778935492233497]

Why 1.5 times the interquartile range? It’s just a rule of thumb, chosen that way because in a normal distribution, over 99% of all data falls within this range. The rest are considered “outliers”.

You can verify this yourself. Take the 10000 samples, and remove the ones that fall within this range. There are only 68 left, so only about 0.7%.

These 68 remaining outliers are drawn each separately as a little circle. They’re vertically spread out randomly so it’s easy to see if there are several of them.

If your data contains big outliers then these can have a disproportianate impact on all kinds of statistical attributes, so it’s good to be immediately aware of them, that’s why they’re drawn separately.

So to recap: the box represents the central 50% of the data, the “whiskers” are the range where most of the rest of the data is expected to be, and the circles are the outliers.

(let [{:keys [q1 iqr q3]} (transduce identity kixi/summary standard-normal-sample)]
  (count (remove #(< (- q1 (* 1.5 iqr))
                     %
                     (+ q3 (* 1.5 iqr)))
                 standard-normal-sample)))
;; => 59

There’s clearly something funny going on with the :height. Seems there are two outliers way beyond all the rest of the data. All of the plots show a bit of outliers, but nothing like this. This might mean we have some errors in our data. Or maybe they really did encounter two abalones that were ten times the size of the others.

Let’s plot the :height vs the :whole-weight. If this abalone is so much bigger it should be heavier too. Those two dots on the far right are definitely suspicious. More probable is that it’s a data entry mistake or a case of missing data, we’ll remove these as well.

Cleaning up your raw data is often a big part of doing data science. I’ll define any cleanup we do as separate transducers, this creates an audit trail, and it allows re-using the same operations in case we get new data.

This looks a lot more reasonable. There’s one more point on the left here that seems a bit far fetched, but it’s not completely in the range of the impossible. Maybe it’s a freak of nature. We’ll leave this one in.

Box plots are great because they can very succinctly summarize a large amount of data, but they can also obscure things like clustering. You have no idea how things are spread out within each quartile.

The lines have some opacity so you can see if multiple lines are drawn on top of each other. Now that we’ve peeked into our data, getting a sense of the general spread of the different variables, it’s time to figure out which one to use to try and predict the amount of rings.

For this I’ll create a “correlation matrix”, this shows for each pair of variables how well they are correlated. The closer to 1 the better, this means that an increase in one variables correlates with an increase in the other variable.

A value close to -1 would also be good, in that case there’s a negative correlation, a downward curve, where an increase in one causes a decrease in the other.

If the result is 0 then there’s no correlation, nothing can be said about the second variable based on the first.

I’ll take all the variables we have, as well as the log of the rings and of the weight measurements. If our analysis so far is correct then the log-weights should correlate strongly with the log-rings.

We’re specifically interested in the rings, so we’ll just look at the pairs containing rings or log-rings, and then sort them by correlation.

There’s a strong correlation between log-rings and rings, but that doesn’t tell us much. After that it gets interesting though.

:log-shell-weight has a 0.74 correlation with :log-rings. That’s quite good!

(let [variables {:rings :rings
                 :log-rings (comp g/ln :rings)
                 :length :length
                 :diameter :diameter
                 :height :height
                 :whole-weight :whole-weight
                 :shucked-weight :shucked-weight
                 :viscera-weight :viscera-weight
                 :shell-weight :shell-weight
                 :log-whole-weight (comp g/ln :whole-weight)
                 :log-shucked-weight (comp g/ln :shucked-weight)
                 :log-viscera-weight (comp g/ln :viscera-weight)
                 :log-shell-weight (comp g/ln :shell-weight)}]
  (->> abalone/data
       (transduce remove-outliers (kixi/correlation-matrix variables))
       (filter #(contains? #{:rings :log-rings} (second (key %))))
       (sort-by val)
       reverse))

Now we are ready to do the actual linear regression. Let’s look again at the scatterplot, what we’re trying to do is draw a line through the middle of this cloud of dots.

That line is the model, it tells you for each value of one variable what the expected value is of the other variable. Now you can compare the real world observations, the dots, with the model, to see how much the model gets wrong. This is called the “error”, the distance between a dot and the line, or the difference between the predicted value and the real observation.

Formally what we’re looking for is a model that minimizes the “mean squared error”. So for each dot you take the error and square it, then add them all up, and divide by the number of dots. That’s the MSE or mean squared error.

(g/open
 (g/scatter-plot {:data (sequence remove-outliers abalone/data)
                  :x (comp g/ln :shell-weight)
                  :y (comp g/ln :rings)}))

So let’s actually do the regression. When there’s only one input variable to predict one output variable, then doing the regression is straightforward and known as a “simple linear regression”, which is built in to kixi.stats.

This is again a reducing function, so you can plug it into transduce, and still have room to plug in a transducer to do any pre-processing.

The result is a vector with two numbers… hmmm. What does that mean? Maybe you remember from high school math that you can describe a straight line with two numbers: a coefficient, and an offset. That’s exactly what this is, one number describes the “slope” of the line, the other tells you how far up or down you need to draw it.

(transduce remove-outliers
           (kixi/simple-linear-regression (comp g/ln :shell-weight)
                                          (comp g/ln :rings))
           abalone/data)
;; => [1.1890320511416592 0.29143092300917883]

So put those two numbers into the formula for a straight line, and you have a function to go from one variable to the other.

This is a nice occasion to use redux’s post-complete to add an extra completion step to kixi’s simple-linear-regression reducing function, which takes those numbers and turns them into a function.

The end result is again a reducing function, one that reduces to a function which is the linear model.

(defn linear-model [fx fy]
  (redux/post-complete (kixi/simple-linear-regression fx fy)
                       (fn [[b a]]
                         #(+ b (* a %)))))

With this you can create the first model, one that derives rings from the height. This combination only had a correlation coefficient of 0.61, let’s see how it performs.

(def height->rings
  (transduce remove-outliers (linear-model :height :rings) abalone/data))

Now you can go over the data again and compare the predicted amount of rings with the actual amount of rings, and compute the Mean Squared Error.

The MSE in this case is 6.5, but what does that number mean? The unit of the output variable is rings, so the error amounts are also in rings, and those are squared, so the MSE in this case is expressed in “rings squared”. When working with data like this regularly ask yourself what units the numbers you come up with carry. Only then can you consider what these numbers mean.

So we have an error amount in “rings squared”. If you take the root of this you get an amount of rings. This “root mean squared error” is a common enough statistic that kixi.stats has it built in, so let’s switch from MSE to RMSE.

What this tells you is that you can expect the model to typically be about 2.6 rings “wrong”. Given that rings have values between 1 and 29 that’s a big error.

(def height->rings
  (transduce remove-outliers (linear-model :height :rings) abalone/data))

(transduce remove-outliers
           (kixi/mse (comp height->rings :height) :rings)
           abalone/data)
;; => 6.527071537294865

(transduce remove-outliers
           (kixi/rmse (comp height->rings :height) :rings)
           abalone/data)
;; => 2.5548134055728737

Let’s try a second model. According to the correlation matrix the best candidate is predicting log-rings by log-shell-weight, so let’s do just that. This has a correlation coefficient of 0.74.

In this case the input of the model is log-shell-weight, so take the shell-weight, transform it to a logarithm, then feed it to the model. The result is now a value in log-rings, so take the exponent to get a value expressed in rings. Now you can compare those to the actual ring counts to compute the errors.

The result is 2.47, which is indeed better than the 2.55 of the previous model, although admittedly not a huge difference.

(def log-shell-weight->log-rings
  (transduce remove-outliers
             (linear-model (comp g/ln :shell-weight)
                           (comp g/ln :rings))
             abalone/data))

(transduce remove-outliers
           (kixi/rmse (comp g/exp log-shell-weight->log-rings g/ln :shell-weight) :rings)
           abalone/data)
;; => 2.4675436415202974

You have to be careful here when comparing models like this that you’re comparing the same type of errors. You might be tempted to do something like this, comparing the output of the model directly with the value of log-rings,

Now the RMSE is in log-rings, so you take the exponent of the final result, assuming this gives you an RMSE expressed in rings again, so you can compare it to the other model, but that’s not the case.

In this case the errors that are being squared are in log-rings, which means the errors on the high end will be downplayed compared to the errors on the low end, which is why you end up with such a vastly lower number.

So: only compare MSE or RMSE when the errors you’re squaring have the same unit.

(g/exp
 (transduce remove-outliers
            (kixi/rmse (comp log-shell-weight->log-rings g/ln :shell-weight)
                       (comp g/ln :rings))
            abalone/data))
;; => 1.2397025210983978

Finally let’s visualize what we’ve been doing. Take that scatterplot again of log-rings vs log-shell-weight, and overlay it with the line representing the predictive model.

That does seem to cut nicely through the middle of that cloud of dots, so at least by eyeballing it you can see it’s not obviously wrong. It’s always useful to do this, you’d be amazed how many simple mistakes you can catch this way.

(let [graph {:data (sequence remove-outliers abalone/data)
             :x    (comp g/ln :shell-weight)
             :y    (comp g/ln :rings)
             :fx   log-shell-weight->log-rings}]
  (g/open (g/overlay (g/scatter-plot graph)
                     (g/function-plot graph))))

One important side note to consider is that in this case we’ve been using the exact same data to train the model, and to evaluate its fitness. In practice you’ll often see data scientists splitting the data up in training data and test data: one is used to create the model, and the other to validate the model.

The reason they do this is to prevent “overfitting”. Overfitting happens when your model starts to represent the peculiarities of the individual data points, rather than the general tendencies of the population. This leads to a model that is very good at reproducing the data it was trained on, but that performs suboptimally on data it hasn’t seen.

The more advanced your model is the more overfitting becomes a problem. In a linear model it’s practically impossible to have overfitting, which is why I haven’t bothered to split the data set in two.

After creating a model it’s worth asking whether the chosen model type was suitable for the data at hand. Was linear regression the appropriate thing to do here? Maybe the relationship between these variables isn’t linear after all, and we should consider a non-linear model.

One way to answer this question is to plot the “residuals”. They’re basically the same as the “errors” we talked about before, the difference between the predicted value and the actual value. When talking about test data we call these errors, when talking about the data used to train the model, they are residuals.

In this graph the residuals should be distributed randomly around the zero-line. If they form more of a U, or an upside down U, then a linear model was not suitable. In this case that seems fine.

(let [graph {:data (sequence remove-outliers abalone/data)
             :x    (comp g/ln :shell-weight)
             :y    #(- (log-shell-weight->log-rings (g/ln (:shell-weight %)))
                       (g/ln ((g/jitter 0.5) (:rings %))))
             :fx   (constantly 0)}]
  (g/open (g/overlay (g/scatter-plot graph)
                     (g/function-plot graph))))

A final premise of a linear regression is that the residuals should be normally distributed. For this you look at a histogram of the residuals.

It’s a bit of a lopsided graph again, we already concluded this isn’t a perfectly fitting model, but the general shape is there, so I’ll conclude that linear regression was suitable here.!

(let [graph {:data (sequence remove-outliers abalone/data)
             :x    (comp g/ln :shell-weight)
             :y    #(g/exp (- (log-shell-weight->log-rings (g/ln (:shell-weight %)))
                              (g/ln ((g/jitter 0.5) (:rings %)))))}]
  (g/open (g/histogram graph)))
